# Environments

One root module, one state key per environment, one tfvars file per
environment. `var.environment` was already threaded through every resource
name, so a second environment is configuration rather than a refactor — which
is the claim `docs/architecture.md` makes and this directory is what backs it.

```
terraform/
├── envs/
│   ├── dev.tfvars.example          copy to dev.tfvars
│   └── production.tfvars.example   copy to production.tfvars
└── backend.<env>.hcl               generated by scripts/bootstrap-state.sh
```

Both environments share one S3 bucket and one lock table, separated by state
key:

```
s3://<bucket>/autodeployx/dev/terraform.tfstate
s3://<bucket>/autodeployx/production/terraform.tfstate
```

Separate keys, not separate buckets: the bucket is versioned and encrypted and
costs nothing, while a second bucket is a second thing to bootstrap, a second
thing to forget, and a second thing to leave behind on teardown.

## Using them

```bash
make init  ENV=dev
make plan  ENV=dev
make apply ENV=dev
```

or without make:

```bash
terraform -chdir=terraform init -reconfigure -backend-config=backend.dev.hcl
terraform -chdir=terraform plan -var-file=envs/dev.tfvars
```

`-reconfigure` is not optional when switching environments. Without it
Terraform offers to *migrate* the production state into the dev key, which is
a question that looks routine and is not.

## What actually differs

Only cost and blast radius. The topology is identical on purpose — an
environment that does not resemble production does not tell you whether a
change works in production.

| | dev | production |
|---|---|---|
| `environment` | `dev` | `production` |
| `desired_count` | 1 | 1 |
| `log_retention_days` | 1 | 7 |
| `rds_backup_retention_days` | 0 | 1 |
| `budget_thresholds_usd` | `[3, 5, 10]` | `[5, 10, 20]` |
| `enable_slo_alarms` | `false` | `true` |
| OIDC refs | any branch | `main` + `production` environment |

`enable_slo_alarms = false` in dev because an error budget over a service
nobody is using measures nothing, and an alarm that fires on a deliberately
broken test deploy is an alarm you learn to ignore.

The dev OIDC subject is deliberately wider (`ref:refs/heads/*`) so a feature
branch can deploy there. That is a real widening of who can assume the role,
and it is the reason dev gets its own role and its own state rather than
sharing production's.

## Cost

Two environments running continuously is two of everything billable — roughly
double `docs/cost-breakdown.md`. The intended pattern is that dev exists for
the length of a change and is destroyed afterwards:

```bash
make destroy ENV=dev
```
